# ADR-001：食堂储值卡消费系统 MVP 架构决策

- 状态：Accepted
- 日期：2026-09-26
- 决策范围：MVP
- 适用规模：员工 < 500，终端 1～3，单食堂，公司内部自用

## 1. 背景

目标是建设一个公司内部食堂储值消费系统。员工通过手机 Web 页面展示动态二维码，食堂 Linux 工控机连接 USB 扫码枪，扫码后由本地服务自动完成餐次判断、余额校验、扣款、交易流水记录和结果反馈。

系统重点不是传统 POS 收银，而是低人工参与、可无人值守运行的自动餐费扣款终端。

## 2. 核心约束

- 管理后台、员工端均采用 Web。
- 员工一人一账户。
- 员工通过手机号 + 密码登录。
- 消费使用服务端生成的动态二维码。
- 正常消费无需人工输入金额。
- 早餐、午餐、晚餐按后台配置的固定餐费扣款。
- Linux 工控机本地运行扫码代理和后端服务。
- 扫码枪由 Scan Agent 直接读取，不依赖浏览器输入框。
- 所有余额变化必须对应不可删除的资金流水。
- 退款必须形成反向流水，不允许删除原流水。
- 数据库不得直接暴露公网。

## 3. 架构决策

采用：

```text
Go 单体后端
+ React 管理后台
+ React 员工 H5
+ SQLite WAL
+ Linux Scan Agent
+ systemd
+ USB 扫码枪
+ HTTPS 公网访问
```

不采用微服务、Redis、消息队列和独立数据库服务器。

### 3.1 原因

当前系统规模较小，业务链路短，单机即可满足性能和可靠性要求。单体服务能降低部署、升级、备份和现场运维复杂度。

SQLite WAL 在 <500 人、1～3 个终端、统一由单后端写入的前提下足够使用，同时具备备份简单、恢复直接、无额外数据库进程等优点。

## 4. 部署结构

```text
员工手机
   │
   │ HTTPS
   ▼
反向代理 / 安全隧道
   │
   ▼
Go Server
   ├── React 管理后台
   ├── React 员工 H5
   ├── SQLite WAL
   ├── 动态二维码服务
   ├── 账务服务
   ├── 日结服务
   └── 终端状态服务

USB 扫码枪
   │
   ▼
Scan Agent
   │
   ▼
Go Server
```

## 5. 账户与账务决策

MVP 使用单余额账户。

账户表保存实时余额，资金流水保存：

```text
交易前余额
交易金额
交易后余额
```

金额统一使用整数“分”，禁止使用 float/double。

资金交易类型至少包括：

- `RECHARGE`
- `RECHARGE_REVERSAL`
- `CONSUME`
- `REFUND`
- `BALANCE_ADJUSTMENT`

所有资金变化必须生成流水。

禁止管理员直接修改 `accounts.balance`。

退款只能关联原消费，只支持全额退款，每笔消费最多退款一次。

充值错误使用充值冲正。

余额调整可正可负，但负向调整不得使余额小于 0，并必须填写原因。

## 6. 动态二维码决策

动态二维码由服务端生成。

- 刷新周期：30 秒
- 实际可接受窗口：约 60 秒
- 服务端同时接受当前周期 Token 和上一周期 Token
- Token 至少 128 bit 随机强度
- 二维码不包含姓名、工号、手机号、内部用户 ID
- 数据库只保存 Token Hash
- 每个用户最多保留当前 Token 和上一 Token

员工页面打开期间持续刷新二维码。

允许员工通过公网访问 H5，也允许在食堂外生成二维码。

接受二维码在约 60 秒窗口内被截图转发的风险，MVP 不引入蓝牙、NFC、近场认证等额外防代刷机制。

## 7. Token 幂等决策

同一 Token 的重复提交永远不能重复扣款。

区分：

```text
同一 Token 重放
→ 返回首次处理结果
→ 不再扣款

新 Token + 同餐次再次消费
→ 进入重复餐次提醒
→ 用户可在终端确认继续消费
```

Scan Agent 的本地防抖只用于改善体验，不承担资金安全职责。

## 8. 餐次决策

MVP 默认：

- 早餐
- 午餐
- 晚餐

每个餐次配置：

- 名称
- 开始时间
- 结束时间
- 金额
- 是否启用

餐次时间禁止重叠。

当前不属于任何餐次时，拒绝消费。

餐费修改立即生效，不修改历史交易。

## 9. 重复消费决策

两类重复：

### 9.1 扫码防抖

短时间内的相同扫码直接忽略，不弹窗，不重复扣款。

### 9.2 同餐次重复消费

员工使用新的有效 Token 在同一餐次再次消费时，终端提示：

```text
本餐次已消费，是否继续？
```

用户本人可以点击继续消费。

待确认状态约 30 秒。

该机制定位为提醒，不是强制权限控制。

## 10. 终端决策

终端建立独立 `terminal_id`。

消费流水记录 `terminal_id`。

终端状态至少包括：

- 在线状态
- 扫码枪状态
- 数据库状态
- 语音模块状态
- 最近扫码时间
- 最近成功交易时间

扫码枪断开必须在终端状态屏明确提示。

消费成功后显示约 3 秒：

- 员工照片
- 姓名
- 本次金额
- 剩余余额
- 消费时间

成功进行语音播报，失败使用明显不同的提示音。

外设反馈失败不得回滚已经成功的资金交易。

## 11. 角色与权限

MVP 两类角色：

- 管理员
- 普通员工

支持多个管理员。

MVP 不细分管理员权限，后续可扩展 RBAC。

## 12. 数据导入导出

人员支持 Excel 批量导入：

```text
上传
→ 校验
→ 预览
→ 确认
→ 导入
```

相同工号允许选择覆盖策略。

允许部分成功，并生成错误报告。

支持导出：

- 人员
- 账户余额
- 充值流水
- 消费流水
- 退款流水
- 余额调整
- 日结结果

## 13. 日结与审计

每天 00:00 日结：

```text
期初余额
+ 当日充值
- 当日消费
+ 当日退款
± 当日余额调整
= 理论期末余额
```

并与所有账户实际余额总和进行比对。

不一致时生成严重告警，禁止系统自动修正。

管理员关键操作写入不可删除的审计日志。

## 14. 备份决策

SQLite 每日自动备份，保留 7 天。

至少保留：

```text
本机备份
+
U盘 / NAS / 外部存储
```

后台提供“立即备份”。

数据库恢复只通过管理员命令行执行，不在普通 Web 页面开放恢复按钮。

## 15. Linux 服务决策

使用 systemd：

```text
canteen-server.service
scan-agent.service
```

要求：

- 开机启动
- 异常自动重启
- 日志可查询
- 断电恢复后自动运行

## 16. 不采用的方案

MVP 不采用：

- 微服务
- Redis
- RocketMQ
- PostgreSQL / MySQL
- Docker 作为强制部署方式
- 浏览器输入框接扫码枪
- 实体 IC 卡
- 微信 / 支付宝支付

## 17. 决策结论

MVP 优先保证：

```text
扫码简单
扣款可靠
账务可追溯
资金事务原子
Token 重放幂等
现场部署简单
断电自动恢复
备份可恢复
```

本 ADR 作为 MVP 开发期间的架构基线。涉及账户模型、交易语义、Token 幂等、SQLite、Linux Scan Agent 等关键决策的变更，应新增 ADR，而不是直接修改实现。
