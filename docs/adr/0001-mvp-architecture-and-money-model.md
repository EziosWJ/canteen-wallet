# MVP 架构与资金模型

- 状态：Accepted
- 日期：2026-09-26

本 ADR 记录已确认的 MVP 基线。目标是让单食堂以低人工参与完成员工储值餐费消费，并在出现错误、退款或故障时保留可核对的资金记录。新规格和任务在 GitHub Issues 中维护；本 ADR 不以早期设计目录为实施依据。

## 架构边界

- 设计容量为员工少于 500 人、1～3 台终端、单食堂。现场 Linux 主机运行 Go 单体服务、SQLite WAL 和扫码代理；员工 H5 经 HTTPS 公网访问，终端通过独立凭据访问内部消费接口。
- 采用服务端生成的短时就餐码。页面约每 30 秒刷新；服务端接受当前与上一周期 Token，窗口约 60 秒。Token 至少 128 bit 随机强度，数据库只存 Hash；同一 Token 重放返回首次终态，不再次扣款。
- 员工可在食堂外生成码。试点接受有效窗口内截图转发使用的风险，异常扫码仍需留痕；不引入近场核验。
- 后端不可达时终端拒绝消费，不缓存、不自动补扣。故障供餐由工作人员人工登记，恢复后管理员凭登记记录受审计补录；余额不足时保持待处理异常，不允许负余额。

单机和 SQLite 降低现场部署、备份与恢复成本；容量或高可用要求超出上述边界时重新评估架构。拒绝离线补扣可以避免网络恢复后产生无法当场确认的资金变动。

## 资金与运营边界

- 员工一人一单余额账户；金额用整数分。所有余额变化经单个账务服务在同一数据库事务内更新账户与不可删除流水，余额不得为负。
- 账户资金来自线下已收款的管理员充值，充值引用收款凭据。资金流水类型为充值、充值冲正、消费、消费退款、余额调整、余额退还。在线支付和公司补贴额度不在本次 MVP。
- 只有已登录管理员可全额退还一笔消费；原消费保留，终端没有撤销入口。已全额退款的消费不再计入同餐次重复判断。同餐次每笔再次消费用新 Token 并在终端逐笔确认，不设次数上限；确认是提醒，不是身份核验。

- 离职结清时线下退还余额，记余额退还流水并关户。关户后仅允许管理员对历史消费执行受限退款与相应余额退还，账户仍保持关闭。
- 日结按流水计算理论期末余额并核对账户余额。线下收款复核另由不同于对应录入人的管理员逐笔完成。差异告警且不自动改余额；至少配置两名管理员账号。

> 同餐次再次消费的确认主体与流程已由 [ADR-0003](0003-scan-dedup-and-employee-repeat-confirmation.md) 更新；其余资金规则仍适用。

六类资金变动在首个交付成果中用真实员工会话、动态 Token、消费 API 与模拟扫码枪验证。日结、线下收款复核、人工供餐补录和真实设备在后续 MVP 阶段交付。

## 客户端与运行边界

- 员工 H5 显示本人余额与全部资金流水，并说明线下充值方式。管理后台手机优先设计，同时支持电脑浏览器处理批量表格和对账。核销屏采用独立终端布局和鉴权，只显示结果、金额和必要身份提示，不显示或播报余额。
- 员工首次登录必须修改管理员发放的临时密码。管理员登录的双因素验证见 [ADR-0005](./0005-optional-admin-second-factor-and-bootstrap.md)（该文取代本条原先的“真实试点前启用”要求，改为可选绑定）；资金操作逐笔审计。员工档案不采集身份证号，照片可选。
- 每日备份保留最近 30 份，并保留最近 12 份月度备份；至少一份存于现场主机之外，定期演练恢复。

分离员工、管理员和终端界面，可让公开屏幕只披露完成核销所需的信息。首个交付成果先验证资金状态机；页面稿经审阅后优先接通真实登录、就餐码和流水，Mock 仅用于页面稿审阅。
