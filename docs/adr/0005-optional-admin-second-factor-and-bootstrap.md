# 管理员初始化、可选双因素与消费模式

- 状态：Accepted
- 日期：2026-09-30
- 取代：[ADR-0001](./0001-mvp-architecture-and-money-model.md) 中“真实试点前管理员登录启用双因素验证”一项

本 ADR 记录 SPEC-004 确立的三项决定。ADR-0001 的其余内容继续有效；其中“真实试点前管理员登录启用双因素验证”改为下文所述的可选绑定。

## 背景

ADR-0001 假设管理员登录在真实试点前启用强制双因素，且首个管理员由服务器命令行创建。实际推进中这两点都成了障碍：强制双因素要求每位管理员先跑一次命令行才能登录后台，管理员更换手机或重装验证器后无法自助恢复；而依赖命令行创建首个管理员意味着新部署必须有服务器 shell，与“管理员在后台自助配置”的目标冲突。同时食堂可能只提供一种消费方式（仅有终端扫码，或仅有固定链接自助消费），需要管理员可配置而非硬编码。

## 决定

### 1. 双因素验证是可选绑定

管理员账号可以不带任何第二因素存在，此时只凭密码登录；已绑定 `totp_secret` 的账号每次登录必须提供有效验证码。绑定采用两步：服务端先生成待绑定密钥写入 `totp_pending_secret` 并返回 `otpauth` URI，只有管理员用验证器生成的验证码确认后才写入 `totp_secret`。待绑定密钥不是登录凭据，超过十分钟即失效，因此中途放弃的绑定既不激活也不放宽已有绑定账号的登录要求。更换与解绑需同时提供当前密码和当前验证码；任何绑定变更都在同一事务内注销该管理员的全部会话。CLI 的 `enroll-admin-totp` 保留，用于可选的一次性绑定。

安全边界随之调整：密码成为唯一的常备登录凭据，第二因素只用于降低密码泄露的风险。为弥补这一点，登录失败仍按现有节流处理，安全接口一律 `Cache-Control: no-store`，密码与密钥material不写入日志、审计或任何响应。

### 2. 无管理员时开放一次性初始化入口

管理员数量为零时，`POST /api/bootstrap` 可用，并在单个事务内创建首位管理员、落定消费模式、写入审计，返回可直接使用的会话和 `next_step`。一旦存在管理员，`GET /api/bootstrap/status` 报告不再需要初始化，创建接口返回 409，因此这条入口无法绕过正常的建号流程。并发或重复提交由 SQLite 写锁串行化，只有一个调用成功，其余被拒且不留半成品。`create-admin` 命令行保留为无后台入口时的替代路径。

选择“无管理员时开放”而非“首次启动生成一次性口令”，是因为后者需要额外的口令分发与过期机制，而前者天然只有一次机会，且失败后不存在半开状态。

### 3. 消费模式可配置且至少一种

消费模式（就餐码消费、自助消费）存放在单行表 `consumption_modes`，数据库 CHECK 保证两者不会同时关闭。管理员变更立即生效并写审计；重复写入相同配置不算变更，不写审计。关闭入口时在同一事务内把该入口下尚未确认的扫码请求置为 `MODE_DISABLED`、把自助消费意图置为失败，因此已在途的请求不会被扣款。模式判定只放在重放分支之后，已完成的消费、结果查询、历史流水与退款不受模式变更影响。前端按模式隐藏入口，但隐藏只是展示，服务端在每次消费请求上重新判定。

## 后果

- 迁移后的既有库保留原有绑定，管理员登录行为不变；新库无需命令行即可完成首次配置。
- 遗失验证器不再需要直接改数据库：`recover-admin-totp <username>` 清除该账号的已绑定与待绑定密钥、注销其全部会话并记录审计，不影响其他账号。
- 双因素由强制变为可选，安全强度依赖密码策略与登录节流；若将来试点要求强制，需要在登录与建号路径上重新引入“必须已绑定”的判定，而不是依赖管理员自觉。
- 消费模式的关闭语义需要在新增消费入口时同步维护：新入口必须接入同一套事务内失效逻辑，否则可能出现过期请求被扣款。
